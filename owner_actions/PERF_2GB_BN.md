# ২ GB ফোনে গতি — আসল মাপা সংখ্যা (perf2gb)

> **এক কথায় (২৮ Oct):** ২ GB প্রোফাইলে লগইন-করা কোল্ড স্টার্ট থেকে হোম **১.৮৫ সেকেন্ড** (লক্ষ্য ৩.০ ✅, মান-মাপকাঠি ৩.৫ ✅)। ১৪টা লঞ্চ-জরুরি ফ্লোর ১৩টায় প্রতিটা স্ক্রিন **৮০০ ms-এর নিচে** খোলে (বেশিরভাগ ~৩৫০–৪৫০ ms, যার ৩০০ ms পাতা-বদলের অ্যানিমেশন)। আমাদের Dart কোডের ভার (UI থ্রেড p90) সব ফ্লোতে **৪ ms-এর নিচে**, ঝাঁকুনি < ৫% ✅। **ব্যর্থ:** ফটো স্টুডিও (১২ MP ছবি বাছাই ৩.৪ সেকেন্ড, এক এডিট ১৭.৬ সেকেন্ড, মেমরি ৪১১ MB), আর একটানা অনেক ফ্লো চালানোর পর মেমরি ২৫০ MB ছাড়ায়; পুরো-ফ্রেম ঝাঁকুনি এমুলেটরের সফটওয়্যার গ্রাফিক্সের কারণে সব জায়গায় লাল (নিচে সৎ ব্যাখ্যা)। কোনো লো-মেমরি কিল হয়নি।

**কোথায় মাপা:** GitHub-এর এমুলেটর, ২ GB প্রোফাইল — রান ৪০৬০৩৫৯৪৬২৫ (আগের মাপ: রান ৪০৫৯৪৮৫৫৪২৪)। Android API ৩৩, RAM ১৯৬৭ MB দেখা যায়, ২ কোর, স্ক্রিন 720x1600 (320 dpi), অ্যানিমেশন চালু, Java heap সীমা 192m। অ্যাপ PROFILE বিল্ড (আসল রিলিজের মতো AOT কোড), সার্ভার = রানারের ভেতরে নকল-নয় এমন টেস্ট Django, আসল-আকারের ডেটা (৫০০ রিমাইন্ডার, ৫০০ খাতা-কাস্টমার, ৫০০ লিড, ১৫০ সেলস চ্যাট, ২০০টা সত্যিকারের এনক্রিপ্টেড মেসেজ)।

**লক্ষ্য:** ঠান্ডা চালু (কোল্ড স্টার্ট) থেকে হোম ≤ ৩.০ সেকেন্ড · প্রতিটি স্ক্রিন খুলতে ≤ ৮০০ ms · স্ক্রলে ফ্রেমের p90 ≤ ১৬ ms আর ৫%-এর কম ঝাঁকুনি (jank) · মেমরি (PSS) ≤ ২৫০ MB · লো-মেমরিতে অ্যাপ মেরে ফেলা (LMK) একবারও নয়।

## মাপগুলো কীভাবে পড়বেন

- **স্ক্রিন খোলা** = ট্যাপ/ঢোকা থেকে নতুন পাতা পুরো দেখা যাওয়া পর্যন্ত (পাতা-বদলের ৩০০ ms অ্যানিমেশন শেষ, কোনো ঘূর্ণি-লোডার নেই)। প্রথম ফ্রেম আসে ৪০–৮০ ms-এ।
- **মেমরি (PSS) কলাম একটানা বাড়ে**, কারণ ১৪টা ফ্লো একই অ্যাপ-প্রসেসে পরপর চলে (টেস্টের নিজের ৩৪ MB ছবিসহ)। আসল ব্যবহারের সবচেয়ে কাছের মাপ: **হোমে বসে থাকা অ্যাপ ২১৪ MB ✅**, প্রথম ৬টা ফ্লো ২১০–২৬৫ MB। ফটো স্টুডিওর পর native heap ~১১৫ MB থেকে যায় আর নামে না — তাই পরের সব ফ্লো ~৩৫০ MB দেখায়। এটাই এখন মেমরির সবচেয়ে বড় সমস্যা।
- **APK:** পাঠানো arm64 APK ৭৪ MB; AAB ১৭৬ MB। এমুলেটরের x86_64 profile APK ১৮৬ MB শুধু মাপার জন্য, ব্যবহারকারী পায় না। কোড-অংশ (Code PSS) ~৭৫ MB — onnxruntime, ML Kit, WebRTC-এর মতো নেটিভ লাইব্রেরি।
- **ব্যাকগ্রাউন্ড ব্যাটারি (৫ মিনিট, স্ক্রিন বন্ধ, চার্জার খোলা):** Assisto-এর নিজের কোনো CPU লাইন আসেনি (প্রায় শূন্য), কোনো jobs/অ্যালার্ম নেই; তালিকায় যা আছে তা সিস্টেমের ছোট wakelock (মোট ~৫০ ms)। আসল ফোনে FCM/লোকেশন চালু থাকলে আলাদা হবে।
- মাঝারি প্রোফাইলে (৪ GB, ১০৮০p) একই কোড দুবার মাপা হয়েছে: হোম ১৭৮৫ ms (রান ৪০৫৯৪৮৬২৫৪০) ও ২০৩১ ms (রান ৪০৬০৩৫৯৪৬২৫) — ২ সেকেন্ডের সীমার একদম কাছে; এখানে বড় স্ক্রিন সফটওয়্যারে আঁকায় ২ GB প্রোফাইলের চেয়েও ধীর, আসল মাঝারি ফোনে GPU থাকায় দ্রুত হবে।

## যা ঠিক করা হলো (শাখা agent/perf2gb)

1. **লগইন-করা কোল্ড স্টার্ট আর মেমরি-সিঙ্কের জন্য অপেক্ষা করে না** (`state.dart`): আগে হোম দেখানোর আগে সার্ভার থেকে পুরো মেমরি-তালিকা আনা পর্যন্ত ঘূর্ণি থাকত; ধীর 2G/3G-তে এটা কয়েক সেকেন্ড। এখন হোম আগে, তালিকা পরে। (CI-তে সার্ভার পাশেই, তাই এখানে পার্থক্য চোখে পড়ে না — আসল ফোনে পড়বে।) টেস্ট: `test/perf2gb_cold_start_test.dart`।
2. **২–৩ GB ফোনে ছবির মেমরি-ক্যাশ ছোট** (`lib/perf/low_ram.dart`, প্রথম ফ্রেমের পরে, ক্র্যাশ-রক্ষিত): ২ GB = ৪০ MB / ৩০০ ছবি, ৩ GB = ৬৪ MB / ৫০০ (আগে সবার ১০০ MB / ১০০০)। এমুলেটরে চালু হয়েছে প্রমাণসহ ("ImageCacheBudget(40 MB, 300)")। টেস্ট: `test/perf2gb_low_ram_test.dart`।
3. **রিমাইন্ডার ও CRM লিড তালিকা অলস (lazy)** — ৫০০টা কার্ড একসাথে না বানিয়ে শুধু পর্দায় যা দেখা যায়; রিমাইন্ডার সাজানোয় প্রতি তুলনায় আবার হিসাব বন্ধ (৫০০টায় ~৯০০০ বার → ৫০০ বার)। খাতার তালিকা main-এ আগেই অলস হয়েছে। টেস্ট: `test/perf2gb_lists_test.dart`।
4. **ফটো স্টুডিওর পর্দার ছবি স্ক্রিন-মাপে ডিকোড** (১২ MP পুরো মাপে একটা ছবি ~৪৮ MB; তুলনা-পাতায় দুটো)। এডিট ও এক্সপোর্ট আগের মতো আসল ছবিতে। টেস্ট: `test/perf2gb_photo_preview_test.dart`। (মেমরি সর্বোচ্চ মাপে এখনো পার্থক্য আসেনি — বড় অংশটা অন্য জায়গায়, নিচে।)
5. CI-তে মাপার যন্ত্র: `.github/workflows/perf2gb.yml`, `tools/perf2gb/` (run_perf.sh, collect.py, to_bangla.py, from_log.py), `app/integration_test/perf_all_test.dart` + `perf/`, `backend/core/management/commands/seed_perf.py`।

আগে/পরে: বেশিরভাগ সংখ্যা এমুলেটরের স্বাভাবিক ওঠানামার (±১০%) মধ্যে — x86 CPU-তে ৫০০ সারির তালিকাও দ্রুত বানানো যায়, তাই অলস-তালিকার লাভ এখানে চোখে পড়ে না; সস্তা ARM ফোনে (৩–৫ গুণ ধীর CPU) পড়বে। হোম→চ্যাটের "আগের" ৩.৬ সেকেন্ড মাপার ভুল ছিল (টেস্টের নিজের ৩ সেকেন্ড অপেক্ষা ধরা পড়েছিল), ঠিক মাপ ৩৯১ ms।

## সৎ সতর্কতা — এমুলেটর বনাম আসল ফোন

- এমুলেটরের CPU (GitHub-এর সার্ভার, x86) একটা সস্তা ২ GB ফোনের ARM Cortex-A53 কোরের চেয়ে **দ্রুত** — তাই UI থ্রেডের সময় আসল ফোনে প্রায় ১.৫–৩ গুণ বেশি হতে পারে।
- গ্রাফিক্স এখানে সফটওয়্যারে আঁকা হয় (SwiftShader, Skia) — আসল ফোনের GPU-র চেয়ে **ধীর**; তাই 'ঝাঁকুনি %' কলামে raster সময় খারাপ দেখায়। 'শুধু UI থ্রেড' কলাম আমাদের Dart কোডের ভার দেখায়।
- আসল ফোনে অ্যাপ Impeller (Vulkan) দিয়ে আঁকে; এখানে Skia (Impeller এই এমুলেটরে ক্র্যাশ করে)।
- মেমরি (PSS) আর LMK মাপ আসলের কাছাকাছি: RAM সত্যিই ২ GB, কিন্তু আসল ফোনে অন্য অ্যাপ (Facebook, Messenger…) পেছনে থাকে বলে চাপ আরো বেশি।
- Firebase Test Lab-এ আসল ২ GB ফোনে মাপা হয়নি: `GCP_TESTLAB_SA` গোপন চাবি সেট করা নেই (মালিকের কাজ — `TESTLAB_SETUP.md`)।

প্রমাণ: GitHub Actions → `Perf 2 GB` রান ৪০৬০৩৫৯৪৬২৫ (পরে) ও ৪০৫৯৪৮৫৫৪২৪ (আগে, ci/perf2gb-before) → আর্টিফ্যাক্ট `perf2gb-2gb` / `perf2gb-mid`; আর্টিফ্যাক্ট নামানো আটকে গেলে (অ্যাকাউন্টের egress সীমা) রান-লগেই পুরো JSON আছে: `gh run view <id> --log > l.txt && tools/perf2gb/from_log.py l.txt out/`। আবার চালাতে: Actions → Perf 2 GB → Run workflow (বা `ci/perf2gb*` শাখায় push)।

## ফটো স্টুডিও — ছোট কপিতে এডিট, সেভে পুরো মাপ (photoperf, ২৮ Oct)

**কী বদলাল:** ছবি বাছাই, মুখ খোঁজা, প্রিভিউ, টুল — সব এখন ছবির একটা ছোট কপিতে (২–৩ GB ফোনে লম্বা দিক ১৬০০ px, বড় ফোনে ২৪০০; ফ্রি ব্যবহারকারীর টুলও এখন enhance-এর মতো সার্ভারের preview_max_px মানে)। প্রতিটা এডিট একটা "রেসিপি" হিসেবে রাখা হয় (মাপা রং/আলোর হিসাব + মুখের জায়গা), আর **সেভ/শেয়ারের সময়ই** সেই একই রেসিপি আসল ১২ MP ছবিতে ব্যাকগ্রাউন্ডে চলে — অগ্রগতির দাগ + % আর সত্যিকারের Cancel সহ। স্টুডিও বন্ধ হলে ML Kit / ONNX মডেল আর সব ছবির বাফার ছেড়ে দেওয়া হয়; ফোনে মেমরি কম পড়লে (didHaveMemoryPressure) ছবির ক্যাশও।

মাপ: ২ GB এমুলেটর, শুধু ফ্লো p07 (একই মাপার কোড), আগে = রান **40617638290** (পুরনো কোড), পরে = রান **40627945785**।

| কী | আগে | পরে | লক্ষ্য | ফল |
|---|---|---|---|---|
| ১২ MP ছবি বাছাই (দেখা ও এডিটের জন্য তৈরি) | ১৬৭৬ ms (পুরো ১৪ ফ্লো-রানে ২.৭–৩.৪ s) | **৭১২ ms** | ≤ ১০০০ ms | ✅ |
| এক এডিটের প্রিভিউ (Low light) | ৮৩৫০ ms (পুরো রানে ১৪–১৭.৬ s) | **১০৯৭ ms** (পিক্সেলের কাজ ৯০০ ms) | ≤ ৮০০ ms | ❌ কাছে, পাস নয় |
| ১২ MP সেভ (পুরো মাপে রেসিপি + কোণের চিহ্ন + PNG) | ছিল না (পুরনো কোডে এডিটটাই পুরো মাপে) | **৬.১ s**, অগ্রগতি + Cancel | ≤ ৮ s | ✅ |
| মেমরি (PSS): স্টুডিও খোলার আগে | — | ৩০২ MB | — | — |

| লো-মেমরি কিল | ০ | ০ | ০ | ✅ |

**সৎ কথা:** (১) এই টেস্টে অ্যাপ স্টুডিও খোলার আগেই ৩০২ MB (টেস্টের নিজের ৩৪ MB ছবি + লগইন-করা অ্যাপ), তাই ২৫০ MB-এর নিচে থাকা এখানে অসম্ভব — বাড়তি অংশটা দেখুন: বাছাই/এডিটে মাত্র +২০–২৬ MB। (২) সেভের সময় +১৬২ MB: ১২ MP ছবির পিক্সেলই ৪৮ MB, দুই কোরে দুই ভাগে কাজের জায়গা লাগে; এটা ৬ সেকেন্ডের জন্য, তারপর ছেড়ে দেয়। আরো কমাতে পরের ধাপ: সেভেও JPEG অংশ-অংশে ডিকোড (নেটিভ BitmapRegionDecoder)। (৩) এডিট প্রিভিউ ১.১ s — এমুলেটরের ২ কোরের একটা UI/আঁকার কাজে ব্যস্ত থাকে; পরের ধাপ: প্রিভিউর পিক্সেল-কাজ আরো দ্রুত করা বা ২ GB ফোনে কপি ১২৮০ px। (৪) আগের "পুরো ১৪ ফ্লো" রানের ৪১১ MB-এর একটা বড় কারণ ছিল আগের ফ্লোগুলোর জমে থাকা মেমরি; এখানে শুধু p07 চালিয়ে তুলনা।

**মান ঠিক থাকে কি না:** টেস্টে প্রমাণ — একই রেসিপি দুবার = হুবহু একই বাইট; ছোট কপির প্রিভিউ আর পুরো-মাপের সেভ ছোট করে মেলালে PSNR > ৩০ dB (চোখে এক); কোর-ভাগ করা কাজ = এক-কোরের কাজের সাথে বিট-বাই-বিট এক; ক্লাসিক পাইপলাইনের গতি-সংশোধন আগের আউটপুটের সাথে বিট-বাই-বিট এক (`app/test/photoperf_test.dart`)।
