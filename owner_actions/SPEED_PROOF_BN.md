# প্রতিটি মূল ফিচারের গতি — আসল মাপ (speedproof, ১৭ Nov ২০২৬)

**এক কথায়:** ১৮টা মূল পাতা ২ GB ফোনের মতো এমুলেটরে ঠান্ডা ও গরম দুইভাবেই **৮০০ ms-এর নিচে** খোলে (৩২০–৫৫৮ ms)। মাপতে গিয়ে ৮টা আসল ধীরতা/ত্রুটি পাওয়া গেল এবং ঠিক হলো (নিচে আগে → পরে)। এখন কোনো পাতা ২০%-এর বেশি ধীর হলে CI লাল হয়।

**কীভাবে মাপা:** GitHub এমুলেটর, Android 13, RAM ২ GB, ২ কোর, ৭২০×১৬০০ — PROFILE বিল্ড (রিলিজের মতো AOT কোড; রিলিজ বিল্ড লাইভ সার্ভারে যায় বলে CI-তে চালানো যায় না, আর লাইভে কখনো লোড টেস্ট নয়)। সার্ভার = রানারের ভেতরের টেস্ট Django + ৫০০ রিমাইন্ডার / ৫০০ খাতা-গ্রাহক / ২০০ এনক্রিপ্টেড মেসেজের মতো আসল-আকারের ডেটা। **ঠান্ডা** = অ্যাপ নতুন করে চালুর পর পাতাটা প্রথমবার; **গরম** = সাথে সাথে আবার। "খোলা" = ট্যাপ থেকে পাতা পুরো দেখা যাওয়া (৩০০ ms পাতা-বদলের অ্যানিমেশনসহ, কোনো ঘূর্ণি নেই)। রান: perf2gb **44049733148** (আগের মাপ 44002942576 ও 44031239103)। লগইন-করা কোল্ড স্টার্ট (অ্যাপ বন্ধ → হোম): ১.৫ s।

## যা ধীর ছিল, কেন, কী ঠিক হলো (আগে → পরে)

1. **CCTV লাইভ ভিউ:** গার্ড-ফোন লাইভ-অনুরোধ জানত শুধু ২০ সেকেন্ডের হার্টবিটে → এখন ৪ সেকেন্ডে হালকা প্রশ্ন (সার্ভার থেকে বদলানো যায়, ০ = বন্ধ)। প্রথম ছবি **১৭.৫ s → ৪.৫ s**। খরচ: দোকানের Wi-Fi-তে দিনে ~২০ MB।
2. **চ্যাট খোলা (My Circle):** প্রতিটা মেসেজের "দেখা" আলাদা করে লেখা হতো → একসাথে। ২০০ মেসেজে **৪১৮ SQL → ২০**, সময় ৭৫৩ → ২১০ ms।
3. **প্ল্যান/ক্রেডিট সার্ভার:** দামের কনফিগ প্রতিটা পণ্যের জন্য বারবার হিসাব হতো (এক তালিকায় ১০৭৮ বার)। payments/config **p95 ২৩০১ → ১৪৪ ms**, plans **১৯৬০ → ২৯ ms**।
4. **ক্রেডিট পাতা:** ৪টা সার্ভার-ডাক একটার পর একটা → একসাথে; আর পাতা বন্ধ করলে "Null check" ত্রুটি (setState after dispose) — ঠিক। আগে গরম-খোলা ১০ s-এও শেষ হয়নি → এখন ৩৭৩ ms।
5. **হোম ব্যাজ:** একই মুহূর্তে ৩–৪ বার একই ডাক → এখন ১টা ভাগ করে। My Circle তালিকা (২০০ মেসেজ, লোডের মধ্যে) **১০৭৮ → ৫৯০–৭৯৭ ms**।
6. **নিরাপদ যাত্রা শুরু-ফর্ম:** ৬টা সার্ভার-ডাক ধারাবাহিক (~০.৭ s CI-তে, 3G-তে কয়েক সেকেন্ড) → একসাথে।
7. **কুরআন:** ৩টা বড় টেক্সট (~৩.৫ MB) UI থ্রেডেই খোলা ও পড়া হতো — ২ GB এমুলেটরে ২০ সেকেন্ডেও সূরা-তালিকা আসেনি → এখন আলাদা isolate-এ (পাতা আটকায় না)।
8. **ফ্যামিলি কেয়ার "আজ রাতের খবর" প্রিভিউ:** প্রতিবার খুললে প্রতিটা সদস্যের দিন নতুন করে (~৩৫ SQL; লাইভ p50 ৩১৪ / p95 ৫৮৪ ms) → ৫ মিনিট ক্যাশ। (লাইভে deploy-এর পর মাপা বাকি।)
- মাপার যন্ত্রেও দুটো ভুল ধরা পড়ল: perf-এর দুই APK আলাদা চাবিতে সই হতো → পরীক্ষায় লগইন হারাত ("লগইন-করা কোল্ড স্টার্ট" আসলে লগআউট অবস্থায় মাপা হচ্ছিল) — এখন এক চাবি।

## লাইভ সার্ভার (শুধু পড়া, ১০–১৭ Nov access log, লোড টেস্ট নয়)

সব API: n=২২,৭৭৮, p50 ১৯ ms, **p95 ১৩২ ms** ✅। ৩০০ ms-এর বেশি p95: circle/chats ৩৩৯ ms (n=৯২; CI-তে ১৩৭ ms, ৩০ SQL), family/brain/night-news ৫৮৪ ms (উপরের ৮ নম্বর), carecall ৩১১ ms। বাকি মূল ডাক: home/badges ২৬৯, journey/active ৭২, notif/feed ৫০, plans/v2 ১২১, khata ৭৬, shop/watchman ১৯৯ ms। লাইভ বক্সে এজেন্টদের কাজও চলে, তাই কিছুটা ভিড়ের প্রভাব আছে।

## পাহারা (CI)

`tools/speedproof/guard.py` + `tools/speedproof/baseline.json` (এই রানের সংখ্যা): কোনো পাতা আগের চেয়ে **২০%-এর বেশি** (আর ৫০ ms-এর বেশি) ধীর হলে, বা মাপা না গেলে perf2gb লাল। চলে: রোজ রাত ০২:৪০ (ঢাকা) main-এ, আর `ci/speedproof*`-এ commit-এ `[speedproof]` লিখলে। সার্ভারের প্রতিটি ডাকের সময় + SQL সংখ্যা CI-তে লেখা হয় (`core/ci_timing.py`, শুধু CI)।
